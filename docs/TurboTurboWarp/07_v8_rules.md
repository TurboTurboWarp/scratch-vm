# 07 V8 向け出力規則（計測に基づく。エミッタはこれに従う）

## 1. 確認済みの事実 (Node 22 / V8 12.4)
- F1 `Float64Array` スロットに変数を置いても速くならない (mandel 33ms)。**JS ローカルへの昇格**で初めて 2x (16ms)。
- F2 PACKED_DOUBLE/SMI の JS 配列は読み書きは速いが、混在 (PACKED_ELEMENTS) への double store は 32x 遅い。push は Float64Array 自前拡張が 3〜4x 速い。
- F3 **OSR + ループ内のコールドな呼出し/未実行サイト → ループ変数が全部タグ付きになり毎反復ボクシング** (1.6 → 5.5 ns/要素)。原因: OSR で入ったループの phi 型付けは loop peeling 頼みで、未実行分岐が `Deoptimize` 出口になるループは peel されない (`--no-turbo-loop-peeling` で raw ループも 5.5ns になることで確認)。通常呼出しで最適化された場合は発生しない。長いループを持つ関数は OSR コードがキャッシュされ使われ続ける。
- F4 共有ヘルパ（`compareEqual` 等）は型フィードバックが全サイトで共有される。

## 2. 規則
- R1 ホットループの高速版には**関数呼出し・プロパティ呼出しを置かない**。コールド値は定数にする (`04 §5` PURE 版)。置かざるを得ないループは一般版として受け入れる（定常状態では問題なし、単発長時間ループでのみ F3 の損）。
- R2 スローパスはモジュールレベル `const` の関数を直接呼ぶ（`R.x(...)` のプロパティロード経由にしない。モジュール先頭で分割代入）。
- R3 比較・キャストの高速路はサイトごとにインライン展開。ヘルパはスローパス専用。
- R4 一時変数は型ごとに分ける。数値ローカルは宣言時に数値で初期化しない場合でも、最初の代入が必ず数値になるようにする。
- R5 オブジェクト形状: `Self`, `F_*`, `TList`, `Thread` はコンストラクタで全フィールドを固定順に初期化。後付けプロパティ禁止。
- R6 `arguments`, `with`, `eval`, `try` を生成関数内で使わない（try は step ループ側のみ）。
- R7 `"use strict"` をモジュール先頭に。

## 3. Pattern Lab（必須タスク）
`test/ttw-bench/patterns/` に、エミッタが出す各パターン（リスト読み 4 形、store、push、mod、比較、入口ガード、フラッシュ）について「生形(ideal)」「採用形」を並べたマイクロベンチを置く。各パターンを (a) 既定フラグ (OSR 支配)、(b) `--no-use-osr` (定常) の両方で測り、採用形が生形の 2.5 倍以内であることを CI で確認。パターンを変える PR はこの数値を添付。V8 更新で結果が変わるため数値は固定せず比率で判定。

## 4. 関数サイズ
V8 は巨大関数を最適化しない（バイトコード約 60KB 上限）。エミッタは IR ノード数で概算し、1 関数 3000 ノード超は文並びの境界で `p_x$part2(S, ...)` に分割（境界で全フラッシュ、ループカウンタは引数/戻り値）。resumable は状態範囲で分割し `fr.pc` の範囲で委譲。

## 5. OSR 対策（P3・任意、計測してから）
単発で 10^6 回以上回るループ向けに、最外ループを「チャンク関数」(4096 反復ごとに return し呼び直す) へ外出しすると 5.5〜8.5 → 2.5〜3.5 ns/要素まで回復することを確認済み。ただし短いループでは呼出し+フラッシュのコストが出るため、既定は無効・ヒューリスティック未確定。
